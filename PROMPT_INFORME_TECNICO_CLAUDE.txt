3. ARQUITECTURA DE LA APLICACIÓN
--------------------------------------------------------------------
Patrón general: aplicación Flask modular por Blueprints, con dos capas de
acceso completamente separadas pero que comparten el mismo modelo de
datos y las mismas reglas de negocio:

a) Capa "web" (app/web/): páginas HTML server-side, autenticadas por
   sesión de cookie de Flask. Pensada para el uso humano normal del
   sistema desde el navegador.
b) Capa "api" (app/api/): API JSON REST bajo el prefijo /api/,
   autenticada por JWT (cabecera Authorization: Bearer), pensada para
   integraciones externas o un futuro cliente distinto (móvil, otro
   frontend).

Ambas capas reutilizan las mismas funciones de reglas de negocio y
autorización (app/utils/permisos.py), evitando duplicar lógica crítica
de seguridad — solo difieren en cómo identifican al usuario autenticado.

Estructura de carpetas real del proyecto:

```
app/
├── __init__.py         Factory create_app(): registra extensiones,
│                        blueprints, exime la API de CSRF, inyecta
│                        usuario_actual y el filtro Jinja hora_ec
├── config.py            Configuración vía variables de entorno (.env),
│                        con validación de variables obligatorias
├── extensions.py        Instancias únicas: db, bcrypt, jwt, cors, csrf,
│                        limiter (evita imports circulares)
├── models/               Usuario, Inventario, InventarioPrevio, Acta,
│                        BienHistorialCustodio, BitacoraAuditoria
├── web/                  Blueprints HTML: auth, inventario, editar, tic,
│                        previo, acta, auditoria, usuarios
├── api/                  Blueprints JSON: auth, bienes, tic, usuarios
│                        (+ decorators.py con guardas JWT propias)
├── utils/                Lógica transversal (detalle en sección 5)
├── templates/            Jinja2: base.html (shell con sidebar) + una
│                        plantilla por página + _macros.html (macro
│                        reutilizable para renderizar campos de
│                        formulario según su tipo)
└── static/               Bootstrap 5 y Bootstrap Icons vendorizados,
                         imágenes institucionales (logos INAMHI)
```

Módulo app/utils/campos.py es la "fuente única de verdad" del proyecto:
define los ~46 campos oficiales del bien de inventario (nombre de
atributo Python, etiqueta oficial en español, a qué pestaña del
formulario pertenece, tipo de dato, qué encabezados alternativos de
Excel se aceptan como alias, y cuáles son obligatorios). Tanto los
formularios web, como la API, como la importación/exportación de Excel,
recorren esta misma lista en vez de tener nombres de columna
duplicados y hardcodeados en varios sitios — decisión de diseño
explícitamente documentada en el código para evitar inconsistencias.

5. MÓDULOS FUNCIONALES (documenta cada uno con su objetivo, sus
   pantallas/endpoints principales y sus reglas de negocio)
--------------------------------------------------------------------

5.1 Autenticación y sesión
- Login web por formulario (usuario + contraseña) contra bcrypt,
  cookie de sesión de Flask; logout limpia la sesión.
- Login API (/api/auth/login) devuelve un JWT; /api/auth/me devuelve
  el usuario autenticado a partir del token.
- Ambas vías de login están limitadas a 10 intentos por minuto por IP
  para mitigar fuerza bruta.
- Tres roles: Administrador, Editor, Tecnico Levantamiento. El
  matching de rol se normaliza (minúsculas + trim) y el rol técnico
  reconoce tanto "tecnico" como "técnico".

5.2 Gestión de Inventario (módulo principal)
- Listado paginado (10 por página) con búsqueda de texto libre y
  filtros avanzados (bodega, estado del bien, custodio, rango de fecha
  de ingreso).
- La búsqueda usa MySQL FULLTEXT (modo booleano, con coincidencia de
  prefijo por palabra) sobre las columnas de texto largo, combinado
  con ILIKE sobre columnas cortas tipo código/estado; en dialectos sin
  soporte FULLTEXT (ej. pruebas con SQLite) cae automáticamente a
  ILIKE puro.
- Alta de un nuevo bien vía modal, con formulario dividido en 4
  pestañas (Identificación, Valoración, Características y Condición,
  Ubicación y Custodia) siguiendo la agrupación de app/utils/campos.py.
  Valida que el Código del Bien sea único y que los campos marcados
  como obligatorios estén completos antes de crear el registro; el
  bien nace en estado "En Revisión".
- Edición de un bien existente: formulario igual al de alta, con dos
  acciones — "Guardar como Borrador" (sin exigir campos obligatorios)
  o "Enviar para Revisión" (exige todos los campos obligatorios,
  validado tanto en el navegador como en el servidor). Un bien en
  estado Aprobado solo puede editarlo Administrador o Editor; además
  puede editarlo quien lo registró originalmente, el custodio actual
  asignado, o cualquier usuario con rol Técnico Levantamiento (mientras
  el bien no esté Aprobado).
- Ciertos campos de custodia/acta (Custodio Activo, Origen del
  Ingreso, Tipo de Ingreso, Nro de Compromiso, Estado del Acta) solo
  pueden crearlos/editarlos el Administrador; el resto de roles los ve
  de solo lectura.
- Cada cambio de "Custodio Actual" queda registrado automáticamente en
  bien_historial_custodio (quién lo tenía, a quién pasó, quién hizo el
  cambio, cuándo), visible como tabla de trazabilidad en la pantalla
  de edición.
- Eliminación de un bien: SIEMPRE borrado lógico (eliminado=1), nunca
  DELETE físico; solo el Administrador puede eliminar.
- Exportación a Excel (.xlsx) del inventario completo o filtrado,
  respetando el orden oficial de columnas, con formato de tabla nativa
  de Excel (encabezado, filtros, bandas de color, ancho de columna
  automático, formato numérico/fecha).

5.3 Aprobación de Bienes / Bandeja TIC
- Bandeja con KPIs (Pendientes, Observados, Aprobados, Total),
  filtrado por estado y búsqueda de texto, paginado (15 por página).
- Acciones individuales: Aprobar (con nota opcional) u Observar (con
  motivo obligatorio), y sus equivalentes en lote (selección múltiple
  de bienes).
- Solo accesible para Administrador o Editor.
- Cada aprobación/observación queda en la bitácora de auditoría.

5.4 Inventario Previo (staging de cargas de Excel)
- Flujo en dos pasos, nunca directo a producción:
  Excel subido → tabla inventario_previo (staging) → revisión humana
  ("Validar" fila por fila, o "Validar todas las pendientes") →
  "Pasar al Inventario General" (migración/upsert hacia inventario,
  solo de filas ya verificadas).
- El sistema se adapta a CUALQUIER Excel que suba el usuario, no solo
  al formato oficial: cada campo admite varios encabezados candidatos
  (alias); si el Excel trae varias columnas candidatas para el mismo
  campo (p. ej. "Ubicación 2025" y "Ubicación 2024"), se usa la
  primera con dato no vacío por fila.
- Filas sin un código de bien válido (vacías o con valores centinela
  tipo "SIN CODIGO ESBYE", "INGRESAR", "POR DEFINIR", etc.) reciben un
  código provisional único generado por el sistema, en vez de
  descartarse o fusionarse entre sí.
- Si el mismo código aparece repetido varias veces en el Excel, se
  conserva la fila MÁS COMPLETA (más campos llenos), no la primera
  encontrada.
- La migración hace upsert por código: si el bien ya existe, solo
  sobrescribe los campos que el staging trae con dato (nunca borra un
  dato ya existente con un campo vacío del nuevo archivo) — permite
  "complementar" datos con cargas sucesivas.
- Se puede descargar una plantilla Excel oficial en blanco, con los
  encabezados correctos y las columnas obligatorias resaltadas.
- Solo accesible para Administrador o Editor.

5.5 Actas de Custodia (PDF + QR)
- Acta individual por bien: PDF con los datos principales del bien y
  un código QR de verificación (contiene código, nombre del bien,
  serie, custodio y estado), descargable por cualquier usuario
  autenticado desde el listado de inventario.
- Acta consolidada por custodio: reúne TODOS los bienes de un custodio
  en un único PDF apaisado, con tabla de bienes, totales, y bloques de
  firma ("Elaborado por" / "Verifica - Custodio"). Se genera desde un
  modal con autocompletado de nombres de custodio, previsualización en
  vivo (embebida en un iframe vía blob URL, sin persistir nada) y solo
  al confirmar "Generar Acta" se numera y persiste de verdad.
- Cada acta emitida es INMUTABLE: se guarda un snapshot JSON de los
  datos de los bienes en ese momento; reimprimirla desde el historial
  siempre muestra exactamente lo que se firmó, aunque el inventario
  haya cambiado o esos bienes se hayan eliminado después.
- Historial de actas emitidas, buscable por custodio, con reimpresión
  en un clic.
- Solo accesible para Administrador o Editor (salvo la descarga de
  acta individual, disponible a cualquier usuario autenticado).

5.6 Auditoría
- Bitácora de los últimos 200 eventos del sistema, buscable por
  código de bien, usuario, acción o detalle.
- Registra: login/logout, alta/edición/eliminación de bienes,
  aprobación/observación (individual y en lote), exportaciones e
  importaciones de Excel, migraciones, descargas de actas
  individuales/consolidadas/reimpresiones, y respaldos de base de
  datos.
- Solo accesible para Administrador o Editor.

5.7 Gestión de Usuarios
- CRUD de usuarios del sistema (crear, editar datos y rol, cambiar
  contraseña, eliminar), accesible para Administrador y Editor, con
  la salvedad de que SOLO el Administrador puede: eliminar usuarios,
  otorgar el rol Administrador a alguien, o modificar (rol, contraseña,
  datos) una cuenta que ya es Administrador. Esta restricción se
  aplica tanto en el backend (web y API) como ocultando en la interfaz
  las opciones que un Editor no puede ejecutar.
- Un usuario no puede eliminar su propia cuenta.
- Incluye un botón (solo Administrador) para generar y descargar de
  inmediato un respaldo completo de la base de datos (mysqldump),
  quedando registrado en la bitácora de auditoría.

7. API REST
--------------------------------------------------------------------
Documenta en una tabla los endpoints principales de /api/ (todos
devuelven/reciben JSON):

Autenticación (app/api/auth.py):
- POST /api/auth/login → { username, password } → { access_token, usuario }
- GET  /api/auth/me (JWT requerido) → datos del usuario autenticado

Bienes (app/api/bienes.py), todos requieren JWT:
- GET    /api/bienes → lista paginada (?q=, ?estado=, ?pagina=, ?por_pagina=)
- POST   /api/bienes → crea un bien (valida campos obligatorios)
- GET    /api/bienes/<codigo> → detalle de un bien
- PUT/PATCH /api/bienes/<codigo> → edita un bien (respeta permisos y
  campos bloqueados por rol)
- DELETE /api/bienes/<codigo> → borrado lógico (solo Administrador)

TIC (app/api/tic.py), requieren JWT + rol Administrador/Editor:
- POST /api/tic/aprobar → { codigo_bien, nota }
- POST /api/tic/observar → { codigo_bien, motivo }

Usuarios (app/api/usuarios.py), requieren JWT + rol Administrador/Editor
(las restricciones de rol Administrador descritas en 5.7 aplican igual
aquí):
- GET    /api/usuarios
- POST   /api/usuarios
- PUT/PATCH /api/usuarios/<id>
- DELETE /api/usuarios/<id> (solo Administrador)

8. FLUJO DE ESTADOS DE UN BIEN (inclúyelo como diagrama/tabla)
--------------------------------------------------------------------
Borrador → En Revisión → (revisión TIC) → Aprobado
                                        ↘ Observado → (corrección) → En Revisión

- Borrador: el usuario está completando el formulario, sin exigencias
  de campos obligatorios; no es visible para aprobación TIC.
- En Revisión: todos los campos obligatorios están completos; entra a
  la bandeja de aprobación TIC.
- Aprobado: TIC lo validó; queda bloqueado para edición salvo
  Administrador/Editor (o los roles con permiso descritos en 5.2).
- Observado: TIC lo rechazó con un motivo; debe corregirse y reenviarse.

9. PRUEBAS Y CONTROL DE CALIDAD REALIZADO
--------------------------------------------------------------------
Redacta esta sección como el resultado de una auditoría técnica y de
seguridad ya ejecutada sobre el código fuente completo (revisión
manual de todos los módulos backend y todas las plantillas, más
pruebas funcionales automatizadas levantando la aplicación real contra
una base de datos de pruebas). Resultado:

- Se verificó que las ~80 clases de icono (Bootstrap Icons) usadas en
  las plantillas existen todas en la librería vendorizada: sin errores
  visuales de iconografía.
- Se ejecutaron pruebas funcionales end-to-end (login, navegación por
  cada módulo, generación de PDF, flujo completo de creación/edición de
  bienes) sin errores.
- Se identificaron y corrigieron 3 defectos:
  1. [Crítico] Escalación de privilegios: un usuario con rol Editor
     podía crear cuentas con rol Administrador, degradar el rol del
     Administrador real, y resetear su contraseña (toma de control de
     la cuenta), porque las rutas de gestión de usuarios no
     restringían el campo "rol" ni protegían las cuentas ya
     administradoras. Corregido con nuevas reglas de autorización
     (puede_asignar_rol, puede_gestionar_cuenta), aplicadas en backend
     web, backend API, y reflejadas en la interfaz.
  2. [Alto] Creación de bienes sin validar campos obligatorios: el
     formulario de alta marcaba visualmente campos como obligatorios,
     pero el servidor no los exigía (a diferencia de la edición), lo
     que permitía bienes incompletos entrando directo a la cola de
     aprobación TIC. Corregido igualando la validación de alta a la de
     edición, tanto en la web como en la API.
  3. [Medio] El login de la API JSON no tenía límite de intentos,
     mientras que el login web sí, permitiendo fuerza bruta de
     contraseñas sin restricción por esa vía. Corregido aplicando el
     mismo límite (10/min).
- Como mejora funcional, se conectó a la interfaz la generación de
  respaldos de base de datos (ya implementada mas nunca invocada desde
  la aplicación), con un botón dedicado solo para el rol Administrador.
- Todas las correcciones se validaron con pruebas de regresión
  automatizadas antes y después del cambio, confirmando que no se
  rompió ningún flujo existente.

10. INSTALACIÓN Y DESPLIEGUE (resumen operativo)
--------------------------------------------------------------------
- Requisitos: Python 3.11+, MySQL Server 8.x + MySQL Workbench, cliente
  mysqldump disponible en el PATH.
- La base de datos se crea completa ejecutando sql/schema.sql desde
  MySQL Workbench (crea las 6 tablas, sus índices, y un usuario
  Administrador inicial con contraseña ya hasheada).
- Configuración por archivo .env (a partir de .env.example): claves
  secretas de sesión y JWT (distintas entre sí), credenciales de base
  de datos, orígenes CORS permitidos, carpeta y ruta de mysqldump para
  respaldos.
- Arranque: pip install -r requirements.txt && python run.py, sirve en
  http://localhost:5000, redirige automáticamente a /login.
- Pensado para correr como proceso único (no hay orquestación
  multi-worker configurada); si se escala a varios procesos, hay que
  migrar el backend de rate-limiting a un almacenamiento compartido.
